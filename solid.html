Software Design & Architecture

Why do we need design principles?

In software development, requirements always change. Clients ask for new payment options, HR updates calculation formulas, or databases migrate. Badly designed code breaks whenever requirements change. The SOLID principles are proven rules to build code that bends without breaking.

The 3 Deadly Traps of Bad Code Architecture

Described by Robert C. Martin. If your software suffers from these, SOLID is the remedy.

1

Rigidity Hard to Change

Every simple change feels like pushing concrete. Touching one class requires modifying 10 other files across the whole project.

Analogy: A car where to change a flat tire, you must also unbolt the transmission and steering wheel.
2

Fragility Breaks Unexpectedly

When applying a change in one place, totally unrelated parts of the software fail without warning.

Analogy: You turn on your kitchen faucet, and unexpectedly your living room television turns off.
3

Immobility Hard to Reuse

Modules are so tangled with the current application that you cannot extract them to use in another project.

Analogy: A car radio that is permanently welded into the engine block and cannot be placed into another vehicle.

The SOLID Acronym at a Glance

S
Single Responsibility

A class should have only 1 reason to change (one actor/job).

O
Open / Closed

Open for extension, closed for modification.

L
Liskov Substitution

Subclasses must behave reliably when replacing parent classes.

I
Interface Segregation

Don't force a class to depend on methods it does not use.

D
Dependency Inversion

Depend on abstractions (interfaces), not direct concretions.

Letter S

Single Responsibility Principle (SRP)

Rule: "A module or class should have one, and only one, reason to change."

In simple words: Do not build "Swiss Army Knife" monster classes. A class should be dedicated to exactly one specific actor or stakeholder (like Accounting, HR, or Database Storage). When a business user asks for a change, only that person's class should change.

👨‍🍳

Real-World Analogy: The Restaurant Staff

Imagine an Italian restaurant where one single person cooks pasta, acts as the accountant calculating payroll, and cleans the sewer pipes. If that person changes their cleaning detergent, it might accidentally contaminate the pasta sauce! In good restaurants, you hire a Chef, an Accountant, and a Sanitation Expert separately.

Letter O

Open-Closed Principle (OCP)

Rule: "Open for extension, closed for modification."

In simple words: When your app needs a new feature, you should be able to add new code (derive a new class) rather than hacking and editing existing tested code. If a class already works and passes tests, don't keep opening it up with more if/else statements!

🔌

Real-World Analogy: Smartphone and App Store

Your smartphone has an operating system. When you want a new photo filter or game, you don't take a screwdriver, open the phone's circuit board, and solder new chips (modifying). Instead, you install a new app via the standard app interface (extending)!

// Closed for modification, open for extension
public abstract class BankAccount {
    protected String name;
    protected double balance;

    public void deposit(double amount) { this.balance += amount; }
    public double getBalance() { return this.balance; }
    public abstract double withdraw(double amount);
}

// Adding new behaviors without touching BankAccount!
public class CheckingAccount extends BankAccount {
    private double serviceCharge = 5.0;
    public void applyServiceCharge() { balance -= serviceCharge; }
    public double withdraw(double amount) { return balance -= (amount + serviceCharge); }
}

public class SavingsAccount extends BankAccount {
    private double interestRate = 0.03;
    public void computeInterest() { balance += (balance * interestRate); }
    public double withdraw(double amount) { return balance -= amount; }
}
Letter L

Liskov Substitution Principle (LSP)

By Barbara Liskov (1987)

In simple words: If Class B is a subtype of Class A, then you should be able to pass an object of B anywhere A is expected, without breaking the application or getting unexpected surprises.

🔋

Real-World Analogy: AA Batteries & Flashlights

If your flashlight requires standard 1.5V AA batteries, you can replace an alkaline battery with a rechargeable Duracell or Energizer battery. The flashlight doesn't care which brand it is—it turns on normally. If a battery brand suddenly exploded because it changed voltage, it would violate Liskov Substitution!

Letter I

Interface Segregation Principle (ISP)

Rule: "Clients should not be forced to depend on methods they do not use."

In simple words: Better to have several tiny, focused interfaces than one giant bloated "fat" interface. When you force a class to implement an interface method it doesn't need, developers are forced to write dummy code or throw ugly runtime exceptions!

🍽️

Real-World Analogy: Fixed Buffet vs. À La Carte Menu

If a restaurant forces every customer to pay for and accept an all-inclusive ticket with seafood, beef, and dairy (fat interface), a vegetarian or lactose-intolerant person is forced to pay for and discard food they can't eat. Instead, provide separate targeted menu options!

// Clean ISP Solution: Specific interfaces
public interface IOrderProcessor {
    void validateShippingAddress();
    void processOrder();
}

public interface IOnlineOrderProcessor {
    void validateCardInfo();
}

// Cash on delivery only cares about general order methods
public class CashOnDeliveryOrderProcessor implements IOrderProcessor {
    public void validateShippingAddress() { /* Check delivery street */ }
    public void processOrder() { /* Dispatch rider */ }
}

// Online orders implement both interfaces
public class OnlineOrderProcessor implements IOrderProcessor, IOnlineOrderProcessor {
    public void validateShippingAddress() { /* Check delivery street */ }
    public void validateCardInfo() { /* Charge Stripe/PayPal */ }
    public void processOrder() { /* Send confirmation email */ }
}
Letter D

Dependency Inversion Principle (DIP)

Rule: "Depend on abstractions, not on concretions."

In simple words: High-level business logic (e.g., UserManager) should not directly instantiate and depend on low-level plumbing details (e.g., EmailNotifier). Both should shake hands through an abstract interface (INotifier).

💡

Real-World Analogy: Wall Electrical Socket

Your home wall socket is an abstraction (a standard 220V/110V plug interface). You can plug in a lamp, a blender, a phone charger, or a TV. The power plant does not hardwire directly into your lamp. If the lamp breaks, you don't call the power plant to rewire the city!

public class UserManager {

// 1. The abstraction (shake-hands interface)
public interface INotifier {
    void notifyClient(String message);
}

// 2. High-level class depends on INotifier abstraction
public class UserManager {
    private INotifier notifier;

    // Dependency is INJECTED from the outside!
    public UserManager(INotifier notifier) {
        this.notifier = notifier;
    }

    public void changePassword(String newPassword) {
        // change logic...
        this.notifier.notifyClient("Your password has been successfully updated!");
    }
}

// 3. Low-level interchangeable concretions
public class EmailNotifier implements INotifier {
    public void notifyClient(String msg) { System.out.println("Emailing: " + msg); }
}
public class SMSNotifier implements INotifier {
    public void notifyClient(String msg) { System.out.println("SMS sending: " + msg); }
}
public class PopupNotifier implements INotifier {
    public void notifyClient(String msg) { System.out.println("Modal Popup: " + msg); }
}

Student Jargon Buster (Technical Terms in Plain English)

Abstraction:

A contract or blueprint (like an Interface) that says what needs to be done, without caring how it's done.

Concretion:

The actual real class with working code inside (e.g., EmailNotifier vs abstract INotifier).

Actor / Stakeholder:

The specific group or person who asks for software changes (e.g., Accounting team, Human Resources, or DBAs).

Tight Coupling:

When Class A directly relies on Class B. If B changes, A instantly breaks like glued cardboard.

Derived / Subclass:

A child class that extends or inherits from a base parent class.

Dependency Injection:

Instead of creating an object inside your class with new, someone hands it to you through the constructor.
